# F13.2a 目录浏览与资料整理技术设计

> 状态：设计已于 2026-10-21 经用户确认；本记录仅冻结技术方案，生产代码尚未修改，未运行代码测试。

## 1. 目标与范围

本步骤让用户能够浏览项目资料的目录结构，并创建、重命名和移动文件夹，重命名与移动资料，修改资料描述，以及在确认后删除非空文件夹。现有 Resource ID、项目归属、owner、访问范围、资产代次与正文处理机制继续作为权威事实，不另建一套资料身份或权限系统。

复用 F13.1a 的资产生命周期、F13.1b 的正文处理与恢复，以及 F13.1c 的可信用户管理入口。目录和移动操作只改变资料库中的逻辑路径，不搬运实际资产文件，也不触发正文重新提取。

本步骤不实现公共 RPC、Electron Bridge、Renderer 页面（由 F13.2b 交接），不实现搜索、Embedding、向量库、标签、权限编辑、正文历史版本恢复或 Agent 的文件夹管理工具。Node 继续只使用现有 Resource 权限和工具能力。

## 2. 模块关系与主流程

```text
用户资料管理请求（内部可信入口）
              |
              v
     UserResourceService
              |
              v
  路径规范化与目录冲突校验
              |
              v
  ResourceService / ResourceStore
       |                  |
       v                  v
  文件夹记录存储       Resource 事件历史
       |                  |
       +--------+---------+
                v
       StorageService.atomic
                |
       +--------+---------+
       |                  |
   SQLite 提交成功      任一步失败
       |                  |
       v                  v
  更新内存投影状态      全部数据库变更回滚

删除资料 / 递归删除文件夹
              |
              v
  既有 ResourceLifecycle
              |
              v
  文件操作记录、资产安全清理与恢复
```

本步骤新增或修改的是目录持久化、路径变更和批量提交能力；现有可信用户入口、Resource 生命周期、资产清理与正文处理继续复用。这里不增加独立后端进程，也不提前定义桌面 RPC。

## 3. 目录与路径模型

### 3.1 逻辑路径与空文件夹

- Resource 继续以现有 `libraryPath` 保存相对逻辑路径，使用 `normalizeLibraryPath` 规范化，并使用 `libraryPathKey` 比较路径。现有路径比较会进行 NFC 规范化和不区分大小写的比较，本步骤不改变该规则。
- 非空目录由 Resource 路径的父级前缀推导。例如 `papers/experiment/a.pdf` 会产生 `papers` 与 `papers/experiment` 两级目录。
- 为了让用户创建的空文件夹在重启后仍然存在，新增显式文件夹记录。目录浏览结果是显式记录与 Resource 路径推导目录的并集。
- 文件夹使用项目内的规范化相对路径作为身份，不引入 FolderId。文件夹重命名会改变其路径；Resource ID 不随目录变化。

### 3.2 路径不变量与重名规则

同一 Project 内必须始终满足：

1. 活跃 Resource 的完整 `libraryPath` 唯一。
2. 显式文件夹路径唯一，且不能与某个 Resource 的完整路径相同。
3. Resource 文件路径不能成为其他文件或文件夹的父级路径。例如已有文件 `papers` 时，不允许创建 `papers/inner`。
4. 创建嵌套文件夹时，父目录必须存在；禁止把文件夹移动到自身或自身后代目录中。
5. 比较冲突时统一使用 `libraryPathKey`，避免仅大小写不同的路径被当作两个对象。

新建文件夹遇到同名目录时，使用与资料编号一致的可预测编号规则生成可用名称；导入和移动资料遇到目标文件重名时，自动编号且保留原 Resource ID。显式重命名或移动整个文件夹如果会与现有目录树冲突，则返回明确冲突，不自动合并两个目录树。

## 4. 资料组织与生命周期语义

### 4.1 重命名与移动资料

- 重命名资料时，`name` 与 `libraryPath` 的文件名部分一起更新，避免展示名称与目录位置不一致；移动资料时只改变逻辑路径。
- 这些操作通过新的 `resource-organized` Resource 事件记录路径变更；事件可携带新的 `libraryPath`，并仅在重命名时携带新的 `name`。现有事件头和其他事件的 payload 不变。
- 每个受影响的 Resource revision 增加一次。Resource ID、owner、access、`entryRef`、`assetGeneration` 与正文处理状态不变。改名不转换文件内容，也不自动修改声明的 Resource type。
- 更新描述继续复用现有用户元数据更新接口；替换资料继续复用现有替换生命周期，不复制一套文件操作实现。

### 4.2 重命名或移动文件夹

先在当前 Project 的一致快照中计算目录及所有后代的目标路径，并完成全量冲突校验。随后在同一个 `StorageService.atomic` 事务中：

1. 更新涉及的显式文件夹路径记录及其更新时间。
2. 为每个路径发生变化的 Resource 追加 `resource-organized` 事件。
3. 将所有事件历史和文件夹记录一起提交。

ResourceStore 需要提供批量追加能力：在事务内校验每个 Resource 的当前 revision、事件序号和目标路径；持久化成功后再统一更新内存历史与投影。任何校验或数据库写入失败，都不能只更新部分目录或 Resource。文件夹移动不改变实际资产路径，也不重新处理正文。

历史重放必须识别新事件，并在每次路径变更后验证路径规范性及活跃 Resource 之间的唯一性，确保重启恢复与运行期间的约束一致。

### 4.3 删除资料与非空文件夹

- 单个资料的删除必须继续经过现有 `UserResourceService` / `ResourceLifecycle`，复用文件操作记录、逻辑删除、安全清理和中断恢复。不得直接删除 Resource 事件、正文行或资产目录来绕过生命周期。
- 删除空文件夹只移除对应的显式目录记录；由其他 Resource 路径推导出来的目录不单独持久化。
- 删除非空文件夹必须由调用方明确传入递归确认。未确认时返回确认所需的结果，且不修改任何资料或目录。
- 递归删除涉及资产文件操作，不能承诺跨所有文件的全局原子回滚。确认后逐个通过现有生命周期删除；如果中途有失败，则保留仍有内容或尚未清理完成的目录记录，返回成功与失败项目，允许用户重试。不能把部分成功报告为整体成功。

## 5. SQLite 持久化与迁移

当前 Storage schema 为 v4。本步骤将 schema 升至 v5，新增显式文件夹表，最小字段为：

| 字段 | 含义 |
|---|---|
| `project_id` | 文件夹所属 Project |
| `path` | 规范化的相对目录路径 |
| `created_at` | 记录创建时间 |
| `updated_at` | 最近一次组织变更时间 |

以 `(project_id, path)` 作为主键，使用 STRICT 表。路径规范化、父目录存在性和与 Resource 的路径冲突由领域层校验；数据库约束负责保证项目内显式路径记录唯一。

新数据库在初始 Schema 中创建该表；现有 v1–v4 数据库通过事务内的向前迁移创建表并升级到 v5。迁移不得重写或丢弃既有 Resource、Session、Project、文件操作或正文记录。文件夹记录与 Resource 路径事件共用现有 StorageService 事务，避免出现文件夹已改名而部分 Resource 路径未提交的状态。

## 7. 错误与权限边界

目录不存在、路径非法、目标冲突、资料不可用、revision 过期和递归删除未确认等情况必须产生可区分的领域结果，不能静默忽略。F13.2a 只定义内部领域行为；公开错误字段、RPC 名称与运行时校验由后续 F13.2b 单独设计。

目录管理入口只由可信用户服务调用，不把 `actor` 字段当作用户身份凭据，也不向 Node 暴露新增目录创建、移动、重命名或递归删除能力。既有 Resource owner 与 access 检查保持不变；跨 Project 的 Resource ID 不得被目录操作解析或修改。

## 8. DeepSeek Harness 对照

只读检查了 `packages/core/agent-loop/src/tool-calls.ts` 的工具调度与取消收敛机制：取消后停止补充未启动调用，并等待已启动调用结束后再收口。本步骤只借鉴“已开始的操作必须有明确收敛结果”的原则，不引入新的调度器或通用任务队列。资料移动是元数据事务，资料删除则继续交给现有文件操作与恢复机制；两者不混成一个新的生命周期。

## 9. 验收标准

1. 新数据库使用 v5；从 v1、v2、v3、v4 升级后既有数据保持不变，空文件夹记录重启后可恢复。
2. 隐式目录与显式空目录正确合并展示；NFC、大小写与路径前缀冲突均按既有 `libraryPathKey` 规则处理。
3. 创建文件夹、重命名 / 移动资料、重命名 / 移动目录的目标冲突有确定结果，不出现文件与目录占用同一路径的情况。
4. 目录树内有多个 Resource 时，路径变更一次性提交；通过故障注入证明任一事件写入失败都会回滚整组数据库变更，内存投影不出现部分更新。
5. 移动前后 Resource ID、owner、access、资产代次、正文状态及既有引用关联保持不变；不触发正文重新提取。
6. 未确认递归删除时数据完全不变；确认后使用现有生命周期删除；部分失败能准确报告并重试，不绕过资产安全清理。
7. Node 无法通过新增入口管理目录或越权修改资料；跨 Project 访问被拒绝。
8. `pnpm typecheck`、Storage schema 测试、Resource 专项测试与完整 `pnpm test` 通过。实现步骤必须记录本机结果和对应 PR head CI；本设计文档不声称任何测试已运行。
