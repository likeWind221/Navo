# 71：Navo 长程验收四个 Bug 复盘（面试版）

2026-10-07 · 技术细节与证据见 [70：修复笔记](70-bugfix-bug-001-004-longterm.md)，状态以 [Bug 跟踪表](bug-plan.md) 为准，代码见 [PR #33](https://github.com/likeWind221/Navo/pull/33)。

## 背景：问题是怎么被发现的

- Navo 是从零实现的长程任务 Agent 编排框架。Main Agent 负责规划和协调；多个 Node Agent 各自执行一个工作节点；节点之间只能通过 Resource（带 ACL 的共享文件）和 Mailbox（发给 Main 的消息）协作；每个回合的启动和每次完成确认都由人控制。
- 验收场景共 8 个人工回合（加入状态探针后为 9 个）：
  1. Main 规划 evidence → synthesis 两个节点；
  2. evidence 发布测量数据；
  3. synthesis 发现缺少独立验证，上报阻塞；
  4. Main 重规划，新增 validation 节点；
  5. validation 发布复测数据；
  6. Main 把资源共享给 synthesis；
  7. 人工确认后，synthesis 在原 Session 中继续，给出最终推荐。
- 离线 Mock 测试 457 项全部通过，但换成真实 Qwen（qwen3.8-27b，thinking 开启）跑完整链路时，两次都没跑完。四个 Bug 都来自这里。

## 总览

共 13 次真实运行：
- run 1：模型服务不可达，不计；
- run 2：失败，用证据定位出 BUG-001；
- run 3、run 4：通过；
- run 5：BUG-001 再次出现；
- run 6、run 7：加入变化通知后，9 个回合全部通过；
- run 8–11：再加名称解析与 resource_id 枚举。四次续接都读到 validation：run 8 用名称读取，行为正确，被旧断言误判为失败；run 9–11 全部通过。
- run 12、13：把提醒机制重构为通用的 system-reminder，并给 Main 加上节点状态变化提醒，两次都是 9 个回合全部通过、零工具错误。

| ID | 现象 | 根因 | 影响 | 当前状态 |
|---|---|---|---|---|
| BUG-004 | 失败后只剩工具名和一句错误摘要 | 验收脚本不持久化模型输入、工具参数和状态，应用释放后现场丢失 | 其他三个 Bug 无法定位 | 已关闭：真实运行中已用于定位 |
| BUG-001 | 续接的 synthesis 声称看不到新的验证资源 | 长对话中的陈旧结论压过新快照，模型还把资源名称当成 resource_id | 长程链路在最后一步断开，得不到最终推荐 | 已关闭：变化通知后续接 8/8 成功 |
| BUG-003 | Main 在 synthesis 已是 idle 时还说 locked | 人工确认发生在 Main 对话之外，Main 沿用历史中的旧状态 | 误导用户下一步操作 | 已关闭：状态探针 10/10 通过 |
| BUG-002 | 发布文件时报 `Resource source file is unavailable` | 未确定：当时没留下路径和 errno | 严格验收在第 6 回合停止 | 未关闭：诊断缺口已补，run 2–13 未复现 |

处理顺序是刻意安排的：先修 BUG-004 补齐证据，再用证据定位其他三个。

## 面试可背版本

### 开场（约 60 秒）

> 我做的 Navo 是一个人在回路的长程 Agent 编排框架：Main Agent 规划，多个 Node Agent 执行，节点之间通过带 ACL 的资源和邮箱交接。F9.8 阶段，离线 Mock 测试 457 项全绿，但接上真实模型跑完整的 8 回合长程链路，两次都在后半段断掉了，暴露出四个问题。
>
> 我的处理思路分四步。第一步，先补可观测性：把每个回合的模型输入、工具参数和结果、领域状态全部落盘。第二步，用离线测试排除工程层原因。第三步，用真实证据把问题分成三类：“系统没给”“模型没用”“I/O 失败”。第四步，优先用结构性手段修复，提示词只作补充。
>
> 最核心的问题是：节点续接时读不到新共享的资源。证据显示，资源其实已经在上下文里，是模型被自己历史里“验证缺失”的结论压住了。我参考 DeepSeek Harness，把“自上回合以来新增的资源”直接放到最新消息旁边，续接成功率从 2/4 提到 8/8。之后又从结构上消除了“名称当 ID”这类错误：工具同时接受 ID 和唯一名称，并且每次请求都把可见资源写进参数枚举。加固后四次真实运行中，Resource 工具调用零失败。

### BUG-004：失败现场留存不足（已修复）

- **问题**：真实验收失败时，脚本只打印工具名称和一句错误摘要。脚本结束还会释放应用、删除临时 Workspace，模型当时看到了什么、传了什么参数、工具返回了什么，全都没法还原。
- **根因**：两层原因。
  - 验收脚本最初只为“断言是否通过”设计，没把可观测性当作交付物。
  - 工具层为了不向模型泄露内部细节，只保留错误消息，把底层 cause（比如 ENOENT）丢掉了。
- **影响**：后面几个 Bug 都只能猜。比如“看不到新资源”，可能是上下文没传、模型漏读或旧历史干扰，没有证据就分不清；我们甚至一度把 BUG-002 错误归因为“模型猜错文件名”。
- **修复**：
  - 每个人工回合结束后写一个 JSON，包含：每次模型请求的完整消息（去掉推理内容）、工具列表、每次工具调用的参数和结果、错误事件，以及节点状态、资源 ACL、Mailbox、路线版本；失败时另写 `failure.json`。
  - 先落盘再断言，保证断言失败时证据已经存在；证据目录在仓库外，不随 Workspace 删除。
  - 工具失败事件保留 cause 链的 name 和 code（最多 8 层），不保留 cause 的 message，避免写进绝对路径或连接串。
  - 请求快照不含 adapter 配置，因此不含 API Key。
- **结果**：连模型服务挂掉的那次运行也留下了证据；run 2 的 `08-8-resume.json` 直接定位出 BUG-001 的真实原因。
- **一句话**：没有证据就没有根因，所以我先把可观测性当成交付物来做。

### BUG-001：续接节点读不到新资源（已修复，核心问题）

- **问题**：第 8 回合，人工确认 validation 后，让 synthesis 在原 Session 中继续。它又去读旧的 evidence，声称看不到新的验证资源，没能给出要求的 125 ms / 93.5% 结论，整条长程链路在最后一步断开。
- **排查**：有三个候选原因，逐个用证据排除。
  1. 上下文漏传？我写了离线测试：第一回合结束后再授权资源，第二回合的 system prompt 确实列出了新资源的 ID 和元数据，历史也完整。排除。
  2. 在 system prompt 里加一条“回合起点的资源快照优先于更早的结论”，够不够？真实运行续接成功率只有 2/4，不够。
  3. 看真实证据，发现两种失败形态：
     - run 2：模型看到了资源，却把名称 `supplied-validation` 当成 resource_id，连续三次失败后得出“只看得到一个资源”；
     - run 5：模型根本没去读，直接沿用历史里自己说过的“验证缺失”，转头向 Main 要 ID。
- **根因**：不是工程上漏传，而是长对话里的“陈旧结论惯性”。新事实只出现在对话最前面的 system prompt 里，被后面历史中模型自己的结论压住了；同时，工具参数没讲清 ID 和名称的区别，错误信息也没告诉模型该怎么改。
- **修复**（参考 DeepSeek Harness 的两个机制）：
  - **把变化放到最新输入旁**：参考 Harness plan-mode 在回合之间状态变化时追加说明的做法，做成一个通用的 system-reminder 机制。
    - 每个 Turn 开始时，把告知 Agent 的外部事实写进 Session 事件日志（`context-observed`）。
    - 下一个 Turn 从日志里取出上一条，求出新增和变化，渲染成 `<system-reminder>` 块，附在人工消息后面，紧挨模型注意力最集中的位置。
    - Context Builder 保持无状态，只负责“当前状态 + 上次快照 → 快照 + 变化”；状态归事件日志所有，持久化时自动带上。
  - **从结构上消除传参错误**：第一版参考 Harness `tool-fs/src/error.ts`，在错误里告诉模型正确的 ID。之后改成从根上消除这类错误：
    - 四个 Resource 工具的 `resource_id` 同时接受 ID 和唯一名称，由服务端解析；重名时报错并列出候选 ID；只在调用方可见的资源里匹配，不泄露无权访问的资源。
    - 每次模型请求时，框架把该 Session 可见资源的 ID 和唯一名称动态写进 `resource_id` 的 enum，让模型在生成参数时就只能从合法值里选。
  - **验收断言**：续接回合必须成功读到 validation，按工具返回的资源身份判断。
  - 提示规则保留，但只作补充。
- **结果**：
  - 只有提示规则时，续接成功率 2/4（run 2、run 5 失败，run 3、run 4 通过）。
  - 加入变化通知后为 8/8（run 6–13），每次都推荐 A 并引用 125 ms / 93.5%，原 Session 和人工 Gate 保持不变。
  - 名称解析与枚举上线后（run 8–11），所有回合的 Resource 工具调用零失败。run 8 中模型用名称 `validation.txt` 读取，被正确解析。
- **取舍**：Harness 刻意保持请求的工具目录稳定，以便缓存提示前缀。动态 enum 会让工具定义随之变化，但 Navo 的 system 本来每个 Turn 都会重建，缓存在 Turn 边界已经失效；enum 只在 Turn 内注册或删除资源时才额外变化，代价有限。另外用探针验证过：`tool_choice: required` 时值被限定在 enum 内；`auto` 模式下模型也遵循了 enum，但是否属于硬约束取决于推理后端。
- **一句话**：先区分“系统没给”和“模型没用”。证据证明上下文没问题之后，我没有继续堆提示词：先调整信息的位置，再从工具接口上消除这一类错误。

### BUG-003：Main 报告的状态与事实不符（已修复）

- **问题**：人工确认 evidence 后，synthesis 已经从 locked 变成 idle，但 Main 在交接回复里仍说它是 locked，会误导用户的下一步操作。
- **根因**：从代码确认。人工确认发生在 Main 的对话之外，不会写进 Main 的 Session。节点状态要调用 `read_roadmap` 才能拿到，Main 没读，就沿用了早先回合历史里的旧值；提示里也没有规定“先查再报”。
- **取舍**：可以把节点状态直接注入 Main 的 system prompt。但项目原有设计是 Main 通过工具读取权威路线图、提示里不放节点细节，而且有测试断言这一点。所以保持设计，改为约束行为。
- **修复**：
  - Main 规则：人工操作发生在对话之外，之前回合的节点状态、资源访问和 Mailbox 可能已经过期。陈述节点状态或“能否运行”之前，必须在本回合调用 `read_roadmap` 或 `read_node`；没读就明确说“未核实”。
  - run 3 中发现 Main 没读就说 synthesis“可以启动了”（实际还是 locked），因此把规则从“状态”扩展到“能否运行”。
  - 验收加一个探针回合：人工确认 validation 后（synthesis 由 locked 变为 idle），问 Main 当前状态，要求它本回合调用了读取工具，并回答 idle。
  - 只靠提示规则仍依赖模型自觉，所以再复用 BUG-001 的 system-reminder 机制：Main 每个 Turn 开始时，框架把自上回合以来的节点变化（如 synthesis: locked → idle）附在人工消息后。只推送变化，不在 system prompt 里放全量节点状态，与原有设计不冲突。
- **结果**：run 4 到 run 13 的探针 10/10 都先调用 `read_node` 再回答 idle；run 12、13 中 Main 在交接和探针回合都收到了节点状态提醒。run 4 还主动说明之前的 locked 已过时，交接回答里也写了“本回合未重新核实节点状态”。
- **一句话**：多参与方系统里 Agent 的记忆天然会过期，权威状态在 Store 而不在对话里，这和分布式系统“读最新版本、不信缓存”是同一个思路。

### BUG-002：发布文件时报“来源不可用”（诊断已修，原错误未复现）

- **问题**：第二次真实运行的第 6 回合，validation 节点把 validation.txt 发布成资源时，工具返回 `Resource source file is unavailable`。模型随后自己恢复了，但严格验收规定“任何工具错误都判失败”，直接停止。
- **根因**：能确认的是诊断缺陷。旧代码把 realpath 和 stat 的各种失败合成同一句话，丢了路径和 errno，模型传错路径（ENOENT）和磁盘 I/O 问题在输出上完全一样。最初归因为“模型猜错文件名”是没有证据的猜测，已经更正。真正的触发原因至今未能证实。
- **修复**：
  - 错误按 errno 分类并带上 Workspace 相对路径，例如 `Resource source file 'supplied/validation.txt' was not found in the Workspace (ENOENT)`，不暴露绝对路径；模型可见的错误也带上这句，模型可以据此改正。
  - 工具失败事件记录 cause 链（ResourceError → ENOENT）。
  - 离线测试：用不存在的路径注册，确认错误带相对路径和 ENOENT、不含绝对路径，再用正确路径重试能成功。
  - 重新定义验收口径：从“回合内不得有任何工具错误”改为“不得有未恢复的工具错误”。工具报错后，同一回合内同名工具调用成功就算恢复；模型错误、运行时错误仍判失败；所有原始错误照样落盘。run 4 中 `edit_node` 参数错误后改用 `connect` 成功，就是一个可恢复错误的真实样本。
- **结果**：run 2 到 run 7 都没再复现，注册全部用对了路径，因此保持未关闭。
- **后续**：下次再出现时，直接从证据读取实际路径和 errno。如果是 ENOENT 且路径不对，属于模型问题，按 BUG-001 的思路加补救提示；如果路径正确但报 EBUSY/EPERM，属于 Windows 文件锁等 I/O 问题，在发布层加重试。
- **一句话**：Agent 的工具报错是常态，验收应考核恢复能力和结果正确性，同时全量留证据，防止把真问题当成恢复掩盖掉；没复现就不宣称已修复。

### 收尾：方法论五句话

1. **先补可观测性，再定位**：BUG-001 靠落盘的请求快照才查出真因；没有证据时，BUG-002 被错误归因过。
2. **分层排除**：先用离线测试证明工程层正确，再用真实证据定位到模型行为。
3. **结构性修复优先，提示词只作补充**：变化放在最新输入旁、参数语义写清、错误里给补救动作；“只靠提示规则成功率 2/4”是很好的反例数据。
4. **验收口径匹配真实场景**：允许可恢复错误，但全量保留错误证据。
5. **模型有随机性，必须多次复跑**：如实记录每次结果和未覆盖的边界，不把一次通过当成已修复。

## 面试官可能追问的问题

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把所有状态都塞进 system prompt？ | 状态会在回合间变化，全量注入会让上下文膨胀，而且仍会被历史压住；只把增量放在最新消息旁，权威状态由工具现读。 |
| 给出同名资源的 ID 会不会泄露权限？ | 只在调用方可见的资源里匹配，无权访问的私有资源不参与匹配，ACL 边界不变。 |
| 允许可恢复错误会不会把真 Bug 放过？ | 只对工具错误放宽，且必须同名工具后续成功；模型和运行时错误仍判失败，所有错误都落盘可审。 |
| 证据落盘会不会泄露敏感信息？ | 去掉推理内容；请求快照不含 adapter 配置和 API Key；cause 只记 name 和 code，不记 message。 |
| 续接通知的“上一回合可见资源”存在哪？重启怎么办？ | 写在 Session 事件日志里的 `context-observed` 事件中，下一个 Turn 从日志取出求差；F10 持久化事件后，重启也不会丢。第一版曾用服务内的内存 Map，后来重构掉了。 |
| 为什么叫 system-reminder，放在 user 消息里不会被当成人的指令吗？ | 第一句明确声明“这是 Navo Turn 起点数据，不是人的请求”；内容只放 id、名称、状态，并转义 `<` `>`；Node 和 Main 共用同一套渲染。 |
| 为什么 BUG-002 还没关闭？ | 原始触发没有复现，只修了诊断能力；不把“没再出现”当成“已修复”。 |
| 这些问题为什么 Mock 测试发现不了？ | Mock 按脚本返回正确的工具调用，只能验证框架协议；模型用错参数、沿用旧结论，只有真实模型才会暴露。 |
| 8/8 能说明问题已经解决吗？ | 不能证明不再发生，只能说明失败概率明显下降；所以保留证据落盘和验收断言，后续可以扩大复跑次数来统计成功率。 |
| 接受名称不会有歧义吗？ | 只接受可见范围内唯一的名称；重名直接报错并列出候选 ID，不做猜测。 |
| 每次请求改工具 schema，会不会影响缓存？ | 会让工具定义变化，但 Navo 的 system 本来每个 Turn 都会重建；enum 只在可见资源变化时才变，代价有限。 |
