# F9.3.1 节点图设计复审

## 做了什么

用户指出可选的是节点而非整条路径，授权纠正已交付设计。修改 `src/roadmap/model.ts`、`graph.ts`、`errors.ts` 和 `tests/roadmap/graph.spec.ts`；更新后端计划、57 号当前设计及 56 号历史状态说明，由后端串行登记索引。F9.3.1 保持已完成，未推进 F9.3.2。

## 关键决策

- 删除 RoadmapFork/RoadmapPath 和 invalid-branch；RoadmapDefinition 只持有 projectId、nodes、edges。RoadmapNode 包含 nodeId 与显式 requirement。节点的执行状态仍归 NodeStore；这是一项路线参与要求。
- 用户示例直接存六条边 A->B、B->C、C->F、A->D、D->E、E->F；标记 B 可选不会令 C 可选，F 仍等待 C。若 C 可选，F 不等待 C，但仍等待上游必选 B。
- buildRoadmapGraph 先验证身份与枚举、建立邻接关系、Kahn 判环，再按拓扑顺序传播必选祖先集合：向后继传递当前集合，当前节点必选时再加入当前节点。多个入边的祖先取并集，重复项去重；不收集不相关分支的节点。
- 采用全部必选祖先而非仅直接前驱，防止可选节点切断上游门槛，也避免已确认的末端节点掩盖未确认的必选祖先。后续 Board 必须读取这些节点的当前状态，不由本函数伪造执行资格。
- 移除线性路径、禁止交叉边、专属汇合点等非必要限制。普通无环的嵌套分叉/汇合均可表达；条件路由、Loop 和按不同下游区别必选性不属于本次实现。required/optional 在当前 Roadmap 内对该节点一致生效。

## 坑与发现

- 将 soft 改名 optional 不能替代正确的状态归属。旧路径模型虽然通过初版测试，但测试固化了错误语义，已用用户的实际图替换。
- 可选 B 未完成时，后续 C 可以推进（其余必选前置满足后）；B 的工作不会被自动取消、跳过或完成。可选只取消对 B 的等待，不删除图上的边。
- 算法判环 O(V+E)，祖先闭包最坏 O(VE) 时间、O(V²) 空间。当前先保留可检查的直接实现，不声称全流程线性复杂度。
- 接口仍仅面向可信后端类型化输入；未知 JSON 校验、项目存活、人工状态检查、Store 和调度未接入。原 Harness 的协议与投影边界参考继续适用，本次未引入新执行生命周期。
- 验证：`pnpm exec vitest run tests/roadmap/graph.spec.ts` 18 项通过；`pnpm typecheck` 通过。覆盖六节点图、仅 B 可选、仅 C 可选、连续可选、嵌套/交叉边、无关分支、展示顺序、不可变、非法引用/枚举和环。`rg` 检查旧 RoadmapFork/RoadmapPath、forks 和 invalid-branch 在 src/tests 中无残留；差异检查通过。没有扩展运行无关测试。
