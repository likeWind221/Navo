# 计划功能性描述重写与 F3.2 拆分

## 做了什么

- `CLAUDE.md` 新增「计划撰写原则」：计划中的步骤描述只写功能性目标（系统获得什么能力、用户能做什么、产生什么可验证结果），不写实现方式（扩展什么模块、加什么文件）；大 Step 按功能目标拆分子 Step；实现决策进开发记录不进计划。
- `_docs/frontend-plan.md` 重新规划：
  - 修正过期的「当前范围」（原文还停在 F1 时代）：F0–F2 已完成真实流式对话，F3.1 契约已冻结，当前进入 F3。
  - F0–F2、F3.1、F3.3–F3.6 的步骤简述全部从“扩展/修改什么”改写为功能性目标；F2 各步的完成标准同步改为用户/系统视角的可验证结果。
  - F3.2 由「后端事件出口」改名为「后端事件与 RPC 对齐」，描述改为“让后端 Agent 的实际输出与新增的 RPC 契约对齐，使 RPC 能够正常把相应事件结果传输给前端”。
  - F3.2 按功能目标拆为四个子步骤：F3.2.1 助手内容事件接通、F3.2.2 工具执行事件接通、F3.2.3 会话命令流与 /hello 命令、F3.2.4 Mock 场景与交接验收。
  - 同步更新「后端交接与实施边界」与「当前下一步」。

## 关键决策

- F3.2 的第一个命令确定为 `/hello` 占位命令：执行后只发布一条“你好”通知，不做其他真实行为（不进入模型上下文、不修改会话、无副作用）；`/clear`、`/model`、`/compact` 等真实命令后续按需加入。因此 F3.2 不再需要动 Session 核心的清空能力。
- F3.2 子步骤先登记在前端计划（沿用 F2 计划枚举后端所有步骤的先例）；`backend-plan.md` 的对应章节由后端 Agent 开始 F3.2.1 时自行补登，本次不改该文件。
- 拆分维度是功能目标（内容事件 → 工具事件 → 命令流 → Mock 交接），每个子步骤可独立审查与验证，不按文件/模块层次拆。

## 坑与发现

- 原 F2/F3 步骤描述把“做什么”和“怎么做”混在一起，“观察出口”“扩展 Runtime/Host”这类内部术语出现在计划里，用户无法从计划判断一个步骤让系统获得什么能力；计划与开发记录的分工需要靠撰写原则固定下来。

## 验证

- 纯文档变更，无代码修改；`frontend-plan.md`、`CLAUDE.md`、`index.md` 交叉检查：F3.2 子步骤编号、`/hello` 表述、F3.1 契约与 F2 先例引用一致，链接相对路径不变。

## 下一步

- 前端 F3.3 可基于 F3.1 冻结契约并行开发桌面桥接与会话状态，验收等待 F3.2.4 的 Mock 场景。
