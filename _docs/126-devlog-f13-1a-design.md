## 1. 目标与范围

建立统一的资料接收与原始文件生命周期管理机制，使用户导入与 Agent 发布复用底层资产保存能力，并保留不同的可信入口和权限。

本阶段负责单文件、多文件、目录导入的领域能力，Resource 身份、创建者、所有者与逻辑路径，原始文件暂存、提交、替换、逻辑删除与物理清理，以及批量结果、取消、持久化恢复、旧调用适配和存量回归。

不负责 UI、Electron RPC、正文提取、Embedding、检索索引或 Agent 检索决策。不新增 Agent 目录导入、内容替换、资料移动或文件夹管理工具；不实现 F13.2 的完整目录管理。重命名、移动的身份不变量在本设计中约束，用户侧整理能力由 F13.2 承接。

本轮仅修订本文件、后端计划与文档索引，不修改生产代码、数据库、前端或公共 RPC 契约，不启动 Step C–E。

## 2. 已冻结的核心决策

### 2.1 Resource ID 是稳定身份

Resource ID 是唯一稳定身份和关联键，不因重命名、移动或内容替换而改变。`name` 是展示名称；`libraryPath` 是逻辑组织位置；`entryRef` 是既有资产引用；内部物理定位不能作为 Agent 任意指定的访问路径。

### 2.2 逻辑路径唯一，允许不同目录同名

- Resource ID 全局唯一；同一项目内非空、规范化后的 `libraryPath` 唯一，不同目录允许同名。
- 用户重复导入同路径资料时，用户导入入口按 F13.0 生成 `name (1).ext`、`name (2).ext` 等可用路径，编号在扩展名前；底层服务只检测冲突，不擅自命名或覆盖。
- 显式替换走独立操作，不能把重复导入解释为替换。自动编号后的路径仍须在提交事务中检查唯一性；并发撞名不得创建重复路径，入口重新分配可用编号或返回明确失败。
- Agent 发布默认进入根目录；如与已有路径冲突，由发布入口应用 F13.0 的自动编号策略，保留原发布能力，不因新增唯一路径约束使原本允许的同名发布直接失败。底层仍不负责命名。
- 路径统一使用 `/` 和 Unicode NFC；拒绝绝对路径、盘符路径、UNC、空段、`.`、`..`、NUL 与不安全符号链接。Windows 保留名称、尾随点/空格及大小写比较的具体规则须在实施前契约清单中收口，不依赖宿主机默认行为。
- 新导入和新发布资料必须有有效逻辑路径。旧资料允许 `libraryPath = null`，保留原 ID、展示名和 `entryRef`，不得直接从 `name` 强制推导路径；空路径不参加唯一约束。
- 路径唯一性由项目 Resource 聚合与存储事务统一保证；额外索引只能是可从权威状态重建的派生数据，不形成第二套可独立修改的当前状态。

旧名称契约继续按可见范围解析：ID 优先，否则仅在名称唯一可见时解析；比较保留现有 `trim().toLowerCase()` 语义。歧义明确报错，不扩大可见范围。新增逻辑路径使用独立、明确的定位参数，不把旧字符串参数改为“先猜路径再猜名称”，避免改变旧调用语义。

### 2.3 删除采用逻辑删除优先、物理清理可重试

第一阶段在同一 SQLite 事务内提交 `resource-deleted` 事件和清理操作记录。成功后 Resource 立即退出有效集合，禁止后续读取、替换及搜索访问。清理失败不得恢复可访问性。

第二阶段由恢复机制或清理任务删除不再需要的资产。记录绑定操作 ID、Resource ID、明确的资产代次和系统生成的目标位置；重复清理幂等，不能误删后来提交的新代次。旧版本清理失败不影响新版本生效，进程退出后继续恢复。

删除请求的重复执行不得重复生成副作用；同一操作 ID 的重试返回既有结果。旧 Agent 删除接口的 revision 校验与资源不可用错误仍保留，不将“清理幂等”误写为任意旧删除请求均成功。

读取入口、逻辑删除与租约登记必须在同一资源级同步边界内竞争：读取先取得租约则可在删除后完成；删除先提交则新读取被拒绝。物理清理必须等待在途租约释放，不要求读取交付前复验删除状态。具体规则见第 6 节。

### 2.4 所有权、创建来源与用户管理

区分四个事实：`actor` 是可信操作主体，`owner` 是权限所有者，`createdBy` 是最初创建主体，`sourceKind` 是用户导入或 Agent 发布等来源。替换、编辑或移动不自动改变 owner、createdBy 或 sourceKind。

扩展现有 owner 模型，增加明确的本地用户主体，与 Main、Node 区分；不得伪造 Main 身份。首版本地用户主体不引入团队或跨用户账户系统。Agent 操作主体仍仅从 Main / Node 的可信 Session 绑定取得，不能由模型传入用户主体来提权。

权限规则：

1. 用户导入只接受可信桌面调用方授权的源文件或目录；本阶段先定义领域入口与授权参数，桌面桥接由 F13.2b 交付。
2. 用户通过独立管理入口管理本项目全部资料，包括 Agent 所有资料，不用 Agent owner 匹配替代用户权限判断。
3. 用户导入的资料归本地用户所有，默认映射现有 `access.kind = "public"` 的项目内共享语义，不新增 `project` 权限枚举值。
4. Agent 保留现有 owner、Session 绑定、默认私有发布和只读共享规则；Main 可读全部、管理访问范围，但不能因此编辑或删除其他所有者资料。
5. 用户管理权限不传递给 Agent；用户修改 Agent 资料不转移所有权。创建者标记不赋予额外权限。
6. 新主体须覆盖所有者类型、权限校验、历史解析、投影与工具结果。现有 RPC 返回结构不变；无法在旧结构中表达的用户所有资料不能伪装为 Main，须在实施前明确兼容出口或提出串行契约交接，未解决不得宣称兼容验收完成。

## 3. 统一资料接收架构

```text
[User-authorized files / directory]   [Agent Workspace file]
                |                              |
                v                              v
      [Trusted user intake]           [Existing publish entry]
                |                              |
                +---------------+--------------+
                                v
                 [Shared asset intake service]
                                |
                                v
                 [Validate / normalize / conflict]
                                |
                                v
                    [Stage / prepare version]
                                |
                                v
                [Commit Resource + operation in DB]
                                |
                                v
                  [Results / cleanup / recovery]
```

以上是待实施主流程。共享底层保存能力不统一来源授权；用户入口不能成为 Agent 任意读取本机文件的通道。入口专属限制与公共安全校验分别落实。

## 4. 原始文件存储与提交

### 4.1 Resource 元数据与版本语义

沿用现有身份、owner、访问范围、`entryRef`、revision 与事件流。用户描述选填、允许空字符串，不自动生成；现有 Agent 发布输入要求不因用户入口放宽而被无意改变。

| 字段或版本 | 职责 |
|---|---|
| `resourceId` | 稳定身份；沿用当前领域 `id` 与对外 `resourceId` 映射 |
| `libraryPath` | 新资料的规范化逻辑路径；旧资料允许 null |
| `owner` / `createdBy` / `sourceKind` | 权限所有者、最初创建主体与来源 |
| `entryRef` | 既有资产引用，不能改作逻辑路径或任意绝对物理路径 |
| `revision` | Resource 聚合状态版本，按现有事件规则递增，用于乐观并发控制 |
| `assetGeneration` | 原始内容代次，新资料从 1 开始；旧资料无代次时逻辑基线为 0 |
| SQLite Schema 版本 | 数据库表、索引及迁移格式；当前代码支持 v1 → v2，不等于 Resource 事件版本 |
| Resource 事件格式版本 | 事件载荷解析契约；当前为 v3，新增类型不自动要求升级格式版本 |

重命名和逻辑移动不改变 ID 或 assetGeneration；替换使 assetGeneration 递增，并按现有事件规则递增 revision，必须校验 expectedRevision。内容代次独立不意味着替换绕过聚合并发控制。操作阶段、复制进度与清理进度不能凭空增加 Resource revision。

旧资料基线代次 0 继续通过原 `entryRef` 定位，不搬迁即能读取；第一次替换提交代次 1。新版本可以用代次化相对 `entryRef`，内部 `assetPath` 不暴露为 Agent 可控路径。

历史 v3 必须继续可解析，新增事件类型同步修改事件联合、解析器与投影。确需新格式版本时，保留旧版本解析；不得因新增字段直接隔离有效旧项目。旧 owner 与访问范围不迁改，历史创建来源只能依据原创建事件恢复，不得依据最后编辑者猜测。

### 4.2 资产存储与提交

物理路径由系统生成；暂存与已提交文件分离。旧布局 `.navo/assets/<resourceId>/<entryRef>` 保持兼容，不做全量搬迁。新版本目标布局：

```text
.navo/
  assets/<resourceId>/versions/<generation>/source.<ext>
  staging/resource-intake/<operationId>/
```

SQLite 与文件系统不构成跨系统原子事务，按以下顺序协调：

1. 校验来源授权、权限、限制与目标逻辑路径，持久化操作意图和 operationId；新建操作先写入 resourceId 为空的意图记录，再分配 ID 并更新同一条操作记录，完成后才准备文件。替换和删除从意图开始就绑定已有 ID。
2. 复制到受控暂存区，校验文件存在、类型、大小限制及版本目标；普通复制不计算哈希。
3. 将完整文件准备到系统控制的不可变目标版本位置，再将操作记为 prepared；此时文件存在但对 Resource 不可见。独占准备目标，不覆盖现有文件；竞争失败的操作只能清理自己拥有的文件。
4. 在同一 SQLite 事务中重新校验当前资源状态、权限、revision、路径唯一性与操作归属，提交 Resource 创建/替换事件及操作 committed 状态；旧版本清理依据同时持久化。
5. 只有事务成功才切换有效代次并返回成功。事务失败或进程中断，由操作记录辨认未提交目标，保留旧版本并清理本操作副作用。
6. 安全清理暂存和不再需要的旧版本；失败保留可恢复记录。

准备版本文件与写入 prepared 之间也可能中断；恢复通过操作意图、受控目标和权威 Resource 状态核对，不仅依赖操作标签。提交之前旧版本始终有效；提交之后读取入口使用新代次，旧代次只供已经获准的活动读取安全收束，不提供用户版本恢复能力。

### 4.3 替换

替换保持 ID、名称、描述、逻辑路径、owner、创建来源和访问范围。新内容提交前不破坏旧内容；复制、准备或数据库提交失败时旧版本仍可读。新内容成功后旧资产进入安全清理流程。

后续正文处理失败不回滚已提交新原始文件，由 F13.1b 管理。当前代次、逻辑删除与处理代次必须在后续阶段交接，避免旧正文重新成为有效结果。

### 4.4 删除

按第 2.3 节原子提交逻辑删除与清理依据，再执行可恢复物理清理。旧布局代次 0 也必须有明确清理目标；不得只凭 Resource 根目录前缀做宽泛删除。删除后禁止新读取租约和替换；删除提交前已取得租约的读取可完成并交付其固定代次内容，释放租约后再清理对应资产。

### 4.5 文件操作记录

持久化记录至少包括 operationId、操作类型、projectId、resourceId（尚未分配允许为空）、基准 revision、旧/目标代次、系统生成的暂存/目标位置、状态、创建/更新时间及必要的错误、清理信息。分配 resourceId 后先持久化再准备文件；同一操作重试复用该身份，不创建第二份 Resource。

| 状态 | 含义 |
|---|---|
| `staging` | 已记录意图，正在准备文件 |
| `prepared` | 目标不可变版本已就绪，尚未提交 Resource 事实 |
| `committed` | Resource 事件与操作提交标记已原子提交 |
| `cleanup_pending` | 存在旧版本、暂存或未提交资产待清理 |
| `completed` | 成功操作及必要清理完成 |
| `failed` | 已终止且没有未处理副作用；仍有清理不得进入此终态 |
| `cancelled` | 未提交操作已取消且没有未处理副作用；仍有清理时保留 cleanup_pending |

操作记录另存业务结果 pending / succeeded / failed / cancelled，与执行状态分开。cleanup_pending 必须保留业务提交结果或关联提交事件，不能因状态变化丢失“已提交/未提交”的区别。完成清理后，成功项进入 completed，未提交失败项进入 failed，未提交取消项进入 cancelled，不把清理成功当作导入成功。提交成功后的取消不覆盖 succeeded；被取消批次中的已成功项保持成功。

采用独立文件操作记录作为过程进度的唯一恢复来源；Resource 事件流仍是业务事实权威。两者不同职责，不保存可分别修改的两套当前资产状态；提交标记与 Resource 事件同事务。操作表具体 DDL、迁移和事务接口须在第 10.1 节实施前检查中明确。

## 5. 批量导入与取消

逐文件提交，不要求整批原子成功。每个文件独立返回成功及 resourceId、冲突、权限/校验失败、复制/提交失败或取消导致的未处理状态；清理待恢复不能抹去实际业务结果。

用户同目录重名按 F13.0 自动编号，底层拒绝静默覆盖，显式替换独立执行。重试失败项时不重复导入已成功项，operationId 重试与用户主动再次导入是不同操作。

取消后停止启动新文件操作，已提交项保留；尚未提交项停止提交、释放文件资源并清理，无法立即清理的持久化待恢复。已开始操作等待进入明确的提交、补偿或恢复状态后返回；取消与提交竞争以 SQLite 原子提交是否已成功为界，不撤销成功项，也不暴露未提交 Resource。

目录遍历须有明确授权根、递归规则、排除规则和符号链接策略，禁止越出授权目录，禁止导入系统内部存储。遍历取消也应返回明确的批次未枚举状态，不能声称未知后代文件已经逐一列入结果；对已枚举文件逐项报告。

## 6. 持久化与异常恢复

### 6.1 读取与资产代次绑定

一次读取绑定确定的 Resource ID 与 assetGeneration，不在执行中自动切换版本。版本文件不可变；读取租约登记与当前状态检查、替换提交、删除提交及清理资格检查须在同一资源级同步边界内协调，避免检查与登记之间被删除插入，也避免先检查引用计数再无保护删除。

读取入口在同一同步边界内验证资源未删除、调用者权限与目标代次，并登记读取租约；租约登记成功后才打开该代次文件。读取一旦获准便固定到该代次：替换不会把在途读取切换到新版本，逻辑删除也不会取消已获准读取。读取可完成并交付绑定代次的完整内容，不在交付前再次检查删除或替换状态；删除提交先于租约登记则新读取被拒绝。权限在读取入口校验，首版不提供在途读取的即时撤权。所有成功、异常和取消路径均释放租约；物理清理只处理不再有效且没有活动租约的代次。已进入对话的内容无法撤回。

本阶段现有读取按单次缓冲返回；未来流式输出须单独定义取消与已发送内容边界，不能直接把当前单次缓冲的在途读取语义套用到每个 chunk。跨次分页快照一致性归后续检索设计。

重启后不恢复已退出进程的内存租约，根据持久化操作与当前代次判断清理；此前提要求单进程拥有同一项目资产的读写和清理。实施前必须核对现有 Host 的独占保障；若不能保证，需先确定跨进程协调，不能假设其他进程没有活动读取。

### 6.2 异常恢复

- 未提交新建：清理暂存和本操作准备的目标版本，不创建重复资料；本版选择补偿清理，不自动重读用户源路径继续导入。
- 未提交替换：保留当前有效旧版本，清理本操作未提交资产，不回滚其他已成功操作。
- 已提交替换：核对提交事件、有效代次和新文件，再安全清理旧版本。
- 已提交删除：继续清理，不恢复 Resource 可访问性。
- 状态不确定：先查权威数据库，再核对受控文件；不得仅凭目录存在推断提交，禁止猜测覆盖或删除有效版本。
- 已提交新文件缺失/不可读：明确报告资产不可用并保留操作证据，不自动回退旧内容或将清理任务标记成功。

恢复幂等，具体覆盖意图后、复制中、目标准备后但 prepared 前、数据库事务前/后和清理中断。不得靠重新执行 Agent 工具恢复文件操作，不因此隐式启动回合。

## 7. 安全与权限

外部路径、名称、内容均不可信。禁止路径穿越、越界符号链接和未授权读取；用户入口仅能读取可信调用方明确授权的源，Agent 发布仍限制在 Project Workspace。系统生成并校验物理路径，不暴露任意文件操作能力。

所有读取、替换、删除重新校验权限和有效状态，用户管理入口与 Agent owner 检查分离。新增限制不得无意改变既有 Agent 发布行为；公共安全校验可复用，入口专属限制分别配置。

文件大小、批次数量、并发数、清理重试策略通过现有配置机制接入，实施前列出默认值和边界测试。当前设计不宣称这些数值已确定，不增加与本阶段无关的重试框架或后台服务。

## 8. 验收标准

### 8.1 资料身份与路径

1. 单文件、多文件和嵌套目录导入符合契约，重命名、移动、替换保持 ID。
2. 不同目录可同名，同目录重复导入自动编号，显式替换保留 ID；并发自动编号不产生重复路径。
3. 无逻辑路径的旧资料仍按 ID/旧入口读取；重复名称、非文件名展示名称不导致迁移失败。
4. 旧名称解析保持可见 ID 优先、唯一可见名称匹配和歧义拒绝；独立逻辑路径定位不改变旧语义。
5. 重命名/移动不增加 assetGeneration；替换递增代次及聚合 revision，拒绝陈旧 expectedRevision。

### 8.2 权限与兼容

6. 用户导入归明确用户主体，不伪装 Main；用户可管理本项目全部资料，Agent 无法借此提权。
7. Agent 发布仍受 Workspace 来源限制、默认私有及既有所有者规则约束；同名发布不因唯一路径约束发生能力回退。
8. 旧 Resource CRUD、名称解析、读取与权限回归通过，用户编辑 Agent 资料不转移 owner/createdBy。
9. 旧 v3 历史及旧物理布局继续可用，不全量迁移；新主体的恢复校验完整。
10. 现有 Resource RPC 返回结构不变、不暴露 assetPath；新增用户主体的兼容出口有明确实现与回归，不伪造 owner。

### 8.3 生命周期与恢复

11. 复制、数据库提交、清理失败均可识别和恢复；替换失败旧版本仍可读。
12. 删除提交后立即禁止新访问；清理失败可重试，不误删有效新代次，重复操作不重复副作用。
13. 批量部分失败、取消、失败项重试返回真实结果；遍历取消不伪造未枚举清单。
14. 活动读取不会被提前清理、不混合代次；删除提交前已取得租约的读取可完整完成，删除先于租约登记则读取拒绝；替换不会切换已获准读取的代次；权限在读取入口校验，首版不提供在途即时撤权。
15. cleanup_pending 仍能辨认提交结果；失败/取消项清理完成不变成导入成功。

### 8.4 数据与异常测试

16. SQLite Schema v1/v2 升级至目标 Schema 与旧 Resource v3 回放分别验证；迁移可重复打开，不改旧 revision/身份。
17. 关键提交步骤模拟真实进程中断，重启核对数据库与文件；不能只用普通抛异常代替中断验证。
18. 路径穿越、符号链接、Windows 路径、保留名称、Unicode/大小写冲突及未授权源读取测试通过。
19. 单进程独占或等价跨进程协调已核实，清理与活动读取并发受同一机制保护。
20. 新增与受影响既有测试通过；原“删除永久保留物理文件”断言更新为逻辑删除、安全清理和失败恢复，不直接删除相关测试。
