# F13.1a：资料接收与原始文件生命周期

**版本：** v1.3（实施契约收口版）  
**日期：** 2026-10-19  
**状态：** Step A 已完成；Step B 实施契约已收口；Step C 实现尚未开始  
**所属阶段：** F13 项目资料库  
**前置阶段：** [F13.0 产品设计](125-devlog-f13-0-design.md)  
**后续阶段：** F13.1b 正文提取与处理恢复

本版在 v1.2 基础上收口实施契约。读取/删除采用方案 B：读取先登记租约并固定资产代次；删除阻止新读取，已获租约的单次读取可完整返回，物理清理等待租约释放。用户资料导入、User owner、用户管理入口及公共 RPC 明确移交 F13.1c；F13.1a 只建设共享资产生命周期内核。旧版 Navo 程序不要求兼容新版数据库或 RPC；本阶段仅考虑从当前 master 基线向前演进，不增加旧版协议适配分支。本文是技术设计，不代表相关能力已实现或测试已通过。

## 1. 目标与范围

建立统一的原始资产生命周期内核，供现有 Agent 发布复用，并供后续 F13.1c 的用户资料补充入口调用。内核负责单文件接收、暂存、不可变版本准备、Resource 事实与操作记录提交、替换、逻辑删除、安全清理及中断恢复。

F13.1a 不实现用户资料选择器、单/多文件或目录导入编排、User owner、用户管理权限及其公共 RPC；这些由 F13.1c 承接。F13.1b 负责正文提取与处理恢复。本阶段不负责 UI、Electron Bridge、Embedding、检索索引或 Agent 检索决策；不新增 Agent 目录导入、内容替换、资料移动或文件夹管理工具。

本轮仅修订技术设计与阶段索引，不修改生产代码、数据库、前端或公共 RPC，不启动 Step C–E。设计要求不代表能力已实现或测试已通过。

## 2. 已冻结的核心决策

### 2.1 Resource ID 是稳定身份

Resource ID 是唯一稳定身份和关联键，不因重命名、移动或内容替换而改变。`name` 是展示名称；`libraryPath` 是逻辑组织位置；`entryRef` 是既有资产引用；内部物理定位不能作为 Agent 任意指定的访问路径。

### 2.2 逻辑路径唯一，允许不同目录同名

- Resource ID 全局唯一；同一项目内非空、规范化后的 `libraryPath` 唯一，不同目录允许同名。
- 用户重复导入同路径资料时，用户导入入口按 F13.0 生成 `name (1).ext`、`name (2).ext` 等可用路径，编号在扩展名前；底层服务只检测冲突，不擅自命名或覆盖。
- 显式替换走独立操作，不能把重复导入解释为替换。自动编号后的路径仍须在提交事务中检查唯一性；并发撞名不得创建重复路径，入口重新分配可用编号或返回明确失败。
- Agent 发布默认进入根目录；如与已有路径冲突，由发布入口应用 F13.0 的自动编号策略，保留原发布能力，不因新增唯一路径约束使原本允许的同名发布直接失败。底层仍不负责命名。
- 路径统一使用 `/` 和 Unicode NFC；拒绝绝对路径、盘符路径、UNC、空段、`.`、`..`、NUL 与不安全符号链接。Windows 保留名称、尾随点/空格及大小写比较的具体规则须在实施前契约清单中收口，不依赖宿主机默认行为。
- 新建与新发布资料必须有有效逻辑路径；本阶段不承诺迁移旧版 Resource 的空路径或旧物理布局。逻辑路径使用 `/` 分隔并按 Unicode NFC 规范化；路径唯一比较统一采用不区分大小写的规范化 key，不依赖宿主机默认行为。拒绝绝对路径、盘符路径、UNC、空段、`.`、`..`、NUL、反斜杠、尾随点/空格、Windows 保留名称及不安全符号链接。
- 路径唯一性由项目 Resource 聚合与存储事务统一保证；额外索引只能是可从权威状态重建的派生数据，不形成第二套可独立修改的当前状态。

旧名称契约继续按可见范围解析：ID 优先，否则仅在名称唯一可见时解析；比较保留现有 `trim().toLowerCase()` 语义。歧义明确报错，不扩大可见范围。新增逻辑路径使用独立、明确的定位参数，不把旧字符串参数改为“先猜路径再猜名称”，避免改变旧调用语义。

### 2.3 删除采用逻辑删除优先、物理清理可重试

第一阶段在同一 SQLite 事务内提交 `resource-deleted` 事件和清理操作记录。成功后 Resource 立即退出有效集合，禁止后续读取、替换及搜索访问。清理失败不得恢复可访问性。

第二阶段由恢复机制或清理任务删除不再需要的资产。记录绑定操作 ID、Resource ID、明确的资产代次和系统生成的目标位置；重复清理幂等，不能误删后来提交的新代次。旧版本清理失败不影响新版本生效，进程退出后继续恢复。

删除请求的重复执行不得重复生成副作用；同一操作 ID 的重试返回既有结果。旧 Agent 删除接口的 revision 校验与资源不可用错误仍保留，不将“清理幂等”误写为任意旧删除请求均成功。

读取入口、逻辑删除与租约登记必须在同一资源级同步边界内竞争：读取先取得租约则可在删除后完成；删除先提交则新读取被拒绝。物理清理必须等待在途租约释放，不要求读取交付前复验删除状态。具体规则见第 6 节。

### 2.4 F13.1a 与用户管理的边界

F13.1a 只使用当前已有的 Main / Node Resource 主体，保证 Agent 发布经过统一资产生命周期内核。它不新增 User 主体，不将用户操作伪装成 Main，也不修改用户侧 RPC。

F13.1c 再统一引入可信的本地 User 主体、最初创建者与来源标记，并提供用户资料导入、用户管理领域入口及公共 RPC。用户管理权限不得传递给 Agent；Agent 的 actor 仍从可信 Session 绑定取得，不能由模型参数伪造。

F13.1a 的底层服务必须将来源授权与文件保存分开：共享保存内核不自行授权任意本机路径。F13.1c 的用户入口只接收桌面调用方明确授权的源文件；Agent 发布继续限制在 Project Workspace。

## 3. 统一资料接收架构

```text
[User-authorized files / directory]   [Agent Workspace file]
                |                              |
                v                              v
      [Trusted user intake]           [Existing publish entry]
                |                              |
                +---------------+--------------+
                                v
                 [Shared asset intake service]
                                |
                                v
                 [Validate / normalize / conflict]
                                |
                                v
                    [Stage / prepare version]
                                |
                                v
                [Commit Resource + operation in DB]
                                |
                                v
                  [Results / cleanup / recovery]
```

以上是待实施主流程。共享底层保存能力不统一来源授权；用户入口不能成为 Agent 任意读取本机文件的通道。入口专属限制与公共安全校验分别落实。

## 4. 原始文件存储与提交

### 4.1 Resource 元数据与版本语义

沿用稳定 Resource ID、owner、访问范围、`entryRef`、revision 与事件流；逻辑路径是独立的组织字段，不是物理路径。用户描述选填、允许空字符串，不自动生成。F13.1a 不改变现有 Agent 发布输入要求；F13.1c 再接入 User owner 与用户入口。

| 字段或版本 | 职责 |
|---|---|
| `resourceId` | 稳定身份；沿用当前领域 `id` 与对外 `resourceId` 映射 |
| `libraryPath` | 必填的规范化逻辑路径；唯一性由同一 Project 的活动 Resource 集合在提交前重新检查 |
| `owner` | F13.1a 仅沿用 Main / Node；`createdBy` 与 `sourceKind` 随 F13.1c 用户资料入口一并定义 |
| `entryRef` | 既有资产引用，不能改作逻辑路径或任意绝对物理路径 |
| `revision` | Resource 聚合状态版本，按现有事件规则递增，用于乐观并发控制 |
| `assetGeneration` | 原始内容代次；新资料从 1 开始，替换成功后递增；不为旧版资料保留代次 0 兼容分支 |
| SQLite Schema 版本 | 当前 master 基线为 v2；F13.1a 增加操作记录表并单向升级到 v3；旧版程序不要求能读取 v3 数据库 |
| Resource 事件格式版本 | 当前 master 为 v3；F13 目标事件格式按新契约统一更新，不保留旧版程序读取新事件的兼容承诺 |

重命名和逻辑移动不改变 ID 或 assetGeneration；替换使 assetGeneration 递增，并按现有事件规则递增 revision，必须校验 expectedRevision。内容代次独立不意味着替换绕过聚合并发控制。操作阶段、复制进度与清理进度不能凭空增加 Resource revision。

新资料统一从代次 1 开始，当前 `entryRef` 指向该不可变代次中的文件。替换创建新的目标代次，提交后更新当前引用；旧代次只在没有活动读取租约且已不再有效时清理。物理路径由系统生成，不能成为 Agent 任意指定的访问路径。

本阶段不增加旧版 Resource 事件、旧物理布局或旧 RPC 的兼容分支。当前审计基线未发现 Resource 事件或有效绑定资产；若实施时发现旧版 Resource 历史，必须明确失败并提示需要重建/清理 Resource 数据，不能悄悄把整个 Project 标记为无效，也不能自动删除用户文件。项目、Session、Node 等其他事件按当前 master 的既有存储升级路径处理。

### 4.2 资产存储与提交

物理路径由系统生成；暂存与已提交文件分离。不兼容旧版物理资产布局；新版本目标布局：

```text
.navo/
  assets/<resourceId>/versions/<generation>/source.<ext>
  staging/resource-intake/<operationId>/
```

SQLite 与文件系统不构成跨系统原子事务，按以下顺序协调：

1. 校验来源授权、权限、限制与目标逻辑路径，持久化操作意图和 operationId；新建操作先写入 resourceId 为空的意图记录，再分配 ID 并更新同一条操作记录，完成后才准备文件。替换和删除从意图开始就绑定已有 ID。
2. 复制到受控暂存区，校验文件存在、类型、大小限制及版本目标；普通复制不计算哈希。
3. 将完整文件准备到系统控制的不可变目标版本位置，再将操作记为 prepared；此时文件存在但对 Resource 不可见。独占准备目标，不覆盖现有文件；竞争失败的操作只能清理自己拥有的文件。
4. 在同一 SQLite 事务中重新校验当前资源状态、权限、revision、路径唯一性与操作归属，提交 Resource 创建/替换事件及操作 committed 状态；旧版本清理依据同时持久化。
5. 只有事务成功才切换有效代次并返回成功。事务失败或进程中断，由操作记录辨认未提交目标，保留旧版本并清理本操作副作用。
6. 安全清理暂存和不再需要的旧版本；失败保留可恢复记录。

准备版本文件与写入 prepared 之间也可能中断；恢复通过操作意图、受控目标和权威 Resource 状态核对，不仅依赖操作标签。提交之前旧版本始终有效；提交之后读取入口使用新代次，旧代次只供已经获准的活动读取安全收束，不提供用户版本恢复能力。

### 4.3 替换

替换保持 ID、名称、描述、逻辑路径、owner、创建来源和访问范围。新内容提交前不破坏旧内容；复制、准备或数据库提交失败时旧版本仍可读。新内容成功后旧资产进入安全清理流程。

后续正文处理失败不回滚已提交新原始文件，由 F13.1b 管理。当前代次、逻辑删除与处理代次必须在后续阶段交接，避免旧正文重新成为有效结果。

### 4.4 删除

按第 2.3 节原子提交逻辑删除与清理依据，再执行可恢复物理清理。旧布局代次 0 也必须有明确清理目标；不得只凭 Resource 根目录前缀做宽泛删除。删除后禁止新读取租约和替换；删除提交前已取得租约的读取可完成并交付其固定代次内容，释放租约后再清理对应资产。

### 4.5 文件操作记录与 SQLite 事务契约

新增 `resource_file_operations` 表，作为文件操作过程进度与重启恢复的唯一来源；Resource 事件流仍是业务事实权威。建议字段固定为：

| 字段 | 职责 |
|---|---|
| `operation_id` | 主键；同一操作重试复用，不得产生第二份副作用 |
| `project_id` / `resource_id` | 项目归属；新建操作分配 ID 前允许 resource_id 为空 |
| `operation_kind` | `create`、`replace` 或 `delete` |
| `execution_state` | `staging`、`prepared`、`committed`、`cleanup_pending`、`completed`、`failed` 或 `cancelled` |
| `business_result` | `pending`、`succeeded`、`failed` 或 `cancelled`；与执行状态分开 |
| `base_revision` / `source_generation` / `target_generation` | 并发校验及资产代次关系 |
| `staging_relpath` / `target_relpath` / `cleanup_targets_json` | 仅存系统生成、可在 `.navo` 下验证的相对目标，不接受调用方任意物理路径 |
| `error_code` / `created_at` / `updated_at` | 诊断与恢复所需信息 |

所有字段使用 SQLite `STRICT` 表及必要的 CHECK 约束；`operation_id` 唯一。新建操作先持久化意图，分配 resourceId 后更新同一记录，再准备文件。操作记录不保存可独立修改的 Resource 当前状态。

扩展现有 `StorageTransaction`，提供操作记录的插入、更新、读取和待恢复查询。使用现有 `StorageService.atomic()`，让 Resource 事件与操作记录的 `committed` 标记在同一个 SQLite 事务中提交；事务失败时两者都不生效。不要另建第二个数据库连接，也不要让文件操作表取代事件流成为业务事实来源。

Schema 由当前 master 的 v2 单向升级到 v3，并在 v3 中新增该表。旧版程序不保证能打开升级后的数据库。F13.1a 不承诺迁移旧版 Resource 历史或旧资产目录；检测到旧版 Resource 历史时应明确拒绝启动并给出可操作错误，不得静默丢弃或误判整个项目。

清理失败时保留 `cleanup_pending` 及原业务结果；Host 启动时和后续生命周期操作前重试待清理记录，不新增常驻后台重试服务。只有没有待处理副作用的操作才能进入 `completed`、`failed` 或 `cancelled` 终态。`cleanup_pending` 不得被解释成导入失败或成功。

`StorageService.atomic()` 负责数据库内的原子性，不把 SQLite 事务延伸到文件复制过程。文件系统与数据库之间仍通过持久化操作意图、不可变目标和恢复流程协调。

## 5. 单文件取消与批量导入交接

F13.1a 提供可取消的单文件生命周期操作，不负责用户侧批量/目录导入编排。F13.1c 负责遍历授权目录、限制批次、调度逐文件操作和汇总结果；每个文件仍独立提交，整批不要求原子成功。

取消单个操作时，若尚未提交则停止提交并清理本操作副作用；若数据库提交已成功，成功结果不可被取消覆盖。取消与提交竞争以同步的 SQLite 提交边界为准。取消后无法立即删除的暂存或目标文件保留在 `cleanup_pending`，由恢复机制继续处理。

用户批次采用以下默认限制，统一配置、统一测试：单文件不超过 100 MiB；每批最多 500 个文件、总量不超过 1 GiB；目录深度最多 32 层；最多 4 个文件并发复制。超限时返回明确的失败原因，不静默跳过。目录符号链接默认不跟随；只处理授权目录内的普通文件。F13.1c 负责目录授权、排除规则和批次结果契约。

## 6. 持久化与异常恢复

### 6.1 Host 单实例与恢复顺序

正式 Host 按当前 OS 用户保持单实例：启动时先取得一个稳定的用户级进程锁，再打开 SQLite 和恢复服务；锁已被占用时，第二个 Host 立即以 `host-already-running` 一类明确错误退出，不进入 ready 状态。使用项目已有的 `proper-lockfile` 依赖实现锁，并在正常退出时释放；进程异常退出后允许锁库按其机制识别失效锁。锁范围不随 Project、Workspace 或 `NAVO_HOME` 改变，因此默认情况下同一时刻只有一个正式 Host 管理这些 Workspace。

Host 必须先取得锁，再打开数据库、执行恢复和接受 RPC。恢复先核对操作记录与 Resource 事实，再重试安全清理；清理失败保留 `cleanup_pending`，不阻止仍然有效的资料使用。

### 6.2 读取与资产代次绑定

一次读取绑定确定的 Resource ID 与 assetGeneration，不在执行中自动切换版本。版本文件不可变；读取租约登记与当前状态检查、替换提交、删除提交及清理资格检查须在同一资源级同步边界内协调，避免检查与登记之间被删除插入，也避免先检查引用计数再无保护删除。

只在工具执行开始时检查一次并不够：检查之后可能发生异步等待，另一条并发请求就在这段间隙删除或替换资料。Host 单实例只能阻止第二个进程，不能阻止同一 Host 内的并发请求。因此读取入口必须在同一资源级同步边界内校验状态并登记租约；租约登记成功后才打开固定代次文件。读取一旦获准便固定到该代次：替换不会把在途读取切换到新版本，逻辑删除也不会取消已获准读取。读取可完成并交付绑定代次的完整内容，不在交付前再次检查删除或替换状态；删除提交先于租约登记则新读取被拒绝。权限在读取入口校验，首版不提供在途读取的即时撤权。所有成功、异常和取消路径均释放租约；物理清理只处理不再有效且没有活动租约的代次。已进入对话的内容无法撤回。

本阶段现有读取按单次缓冲返回；未来流式输出须单独定义取消与已发送内容边界，不能直接把当前单次缓冲的在途读取语义套用到每个 chunk。跨次分页快照一致性归后续检索设计。

重启后不恢复已退出进程的内存租约，根据持久化操作与当前代次判断清理；此前提要求单进程拥有同一项目资产的读写和清理。实施前必须核对现有 Host 的独占保障；若不能保证，需先确定跨进程协调，不能假设其他进程没有活动读取。

### 6.3 异常恢复

- 未提交新建：清理暂存和本操作准备的目标版本，不创建重复资料；本版选择补偿清理，不自动重读用户源路径继续导入。
- 未提交替换：保留当前有效旧版本，清理本操作未提交资产，不回滚其他已成功操作。
- 已提交替换：核对提交事件、有效代次和新文件，再安全清理旧版本。
- 已提交删除：继续清理，不恢复 Resource 可访问性。
- 状态不确定：先查权威数据库，再核对受控文件；不得仅凭目录存在推断提交，禁止猜测覆盖或删除有效版本。
- 已提交新文件缺失/不可读：明确报告资产不可用并保留操作证据，不自动回退旧内容或将清理任务标记成功。

恢复幂等，具体覆盖意图后、复制中、目标准备后但 prepared 前、数据库事务前/后和清理中断。不得靠重新执行 Agent 工具恢复文件操作，不因此隐式启动回合。

## 7. 安全与权限

外部路径、名称、内容均不可信。禁止路径穿越、越界符号链接和未授权读取；用户入口仅能读取可信调用方明确授权的源，Agent 发布仍限制在 Project Workspace。系统生成并校验物理路径，不暴露任意文件操作能力。

所有读取、替换、删除重新校验权限和有效状态，用户管理入口与 Agent owner 检查分离。新增限制不得无意改变既有 Agent 发布行为；公共安全校验可复用，入口专属限制分别配置。

文件大小、批次数量、并发数、清理重试策略通过现有配置机制接入，实施前列出默认值和边界测试。当前设计不宣称这些数值已确定，不增加与本阶段无关的重试框架或后台服务。

## 8. 验收标准

### 8.1 资料身份与路径

1. 单文件、多文件和嵌套目录导入符合契约，重命名、移动、替换保持 ID。
2. 不同目录可同名，同目录重复导入自动编号，显式替换保留 ID；并发自动编号不产生重复路径。
3. 无逻辑路径的旧资料仍按 ID/旧入口读取；重复名称、非文件名展示名称不导致迁移失败。
4. 旧名称解析保持可见 ID 优先、唯一可见名称匹配和歧义拒绝；独立逻辑路径定位不改变旧语义。
5. 重命名/移动不增加 assetGeneration；替换递增代次及聚合 revision，拒绝陈旧 expectedRevision。

### 8.2 权限与兼容

6. 用户导入归明确用户主体，不伪装 Main；用户可管理本项目全部资料，Agent 无法借此提权。
7. Agent 发布仍受 Workspace 来源限制、默认私有及既有所有者规则约束；同名发布不因唯一路径约束发生能力回退。
8. 旧 Resource CRUD、名称解析、读取与权限回归通过，用户编辑 Agent 资料不转移 owner/createdBy。
9. 旧 v3 历史及旧物理布局继续可用，不全量迁移；新主体的恢复校验完整。
10. 现有 Resource RPC 返回结构不变、不暴露 assetPath；新增用户主体的兼容出口有明确实现与回归，不伪造 owner。

### 8.3 生命周期与恢复

11. 复制、数据库提交、清理失败均可识别和恢复；替换失败旧版本仍可读。
12. 删除提交后立即禁止新访问；清理失败可重试，不误删有效新代次，重复操作不重复副作用。
13. 批量部分失败、取消、失败项重试返回真实结果；遍历取消不伪造未枚举清单。
14. 活动读取不会被提前清理、不混合代次；删除提交前已取得租约的读取可完整完成，删除先于租约登记则读取拒绝；替换不会切换已获准读取的代次；权限在读取入口校验，首版不提供在途即时撤权。
15. cleanup_pending 仍能辨认提交结果；失败/取消项清理完成不变成导入成功。

### 8.4 数据与异常测试

16. SQLite Schema v1/v2 升级至目标 Schema 与旧 Resource v3 回放分别验证；迁移可重复打开，不改旧 revision/身份。
17. 关键提交步骤模拟真实进程中断，重启核对数据库与文件；不能只用普通抛异常代替中断验证。
18. 路径穿越、符号链接、Windows 路径、保留名称、Unicode/大小写冲突及未授权源读取测试通过。
19. 单进程独占或等价跨进程协调已核实，清理与活动读取并发受同一机制保护。
20. 新增与受影响既有测试通过；原“删除永久保留物理文件”断言更新为逻辑删除、安全清理和失败恢复，不直接删除相关测试。

验收使用项目声明的 Node ≥24。必须实际执行并报告结果，不凭源码审查宣称通过；本版文档修订不执行代码验收或真实模型实验。

## 10. 后续阶段边界

F13.1a 仅保证原始资料身份、接收、保存与生命周期。F13.1b 负责正文提取、处理状态、失败重试及恢复；F13.3 负责检索索引与召回；F13.4 负责 Agent 检索时机、预算与证据检查。不提前引入 Embedding、向量库或完整 RAG 策略。

### 10.1 已收口的实施契约

1. **用户主体分期：** F13.1a 只支持现有 Main / Node Resource 主体；F13.1c 新增本地 User owner、用户管理领域入口、可信来源授权及公共 RPC。Agent 不得构造 User actor。
2. **数据库事务：** 当前 master Schema v2 单向升级到 v3，新增 `resource_file_operations`；扩展 `StorageTransaction`，Resource 事件和操作 `committed` 标记通过 `StorageService.atomic()` 同事务提交。
3. **旧版边界：** 不保证旧版 Navo 程序能读取新数据库或新 RPC；不增加旧版 Resource 事件、旧物理布局和旧 RPC 结构的兼容分支。检测到无法处理的旧 Resource 历史时显式失败，不静默删除资料或使整个 Project 被误判为无效。
4. **路径规范：** `/` 分隔、Unicode NFC、统一大小写不敏感的唯一 key；拒绝路径穿越、绝对/盘符/UNC 路径、反斜杠、Windows 保留名称、尾随点/空格及不安全符号链接。自动编号放在扩展名前，冲突在提交前再次检查；Agent 发布冲突也由发布入口编号。
5. **读取与删除：** 同一资源级同步边界完成状态检查和租约登记。删除提交后拒绝新租约；已有租约固定版本并可完成；物理清理等待租约释放。首版不做在途即时撤权，也不做交付前删除状态复验。
6. **Host 单实例：** 正式 Host 按 OS 用户保持单实例，在打开数据库和接受 RPC 前取得稳定锁；锁已占用则第二个 Host 立即失败。正常退出释放锁，崩溃后由锁库处理失效锁。
7. **恢复策略：** 操作表是执行进度权威，Resource 事件是业务事实权威；清理失败持久化为 `cleanup_pending`，在 Host 启动和后续生命周期操作前重试，不添加常驻重试服务。
8. **默认限额：** 单文件 100 MiB；用户批次最多 500 个文件、总量 1 GiB、目录深度 32 层、最多 4 个并发复制；目录符号链接不跟随。超限显式失败。
9. **单文件操作边界：** F13.1a 提供单文件生命周期操作；用户多文件/目录遍历、批次取消与结果汇总由 F13.1c 编排；每个文件独立提交，不要求整批原子成功。

以上契约足以开始 F13.1a Step C。实现时若代码审计发现与当前 master 的实际接口冲突，应先报告具体差异，不得自行恢复旧版兼容范围。
